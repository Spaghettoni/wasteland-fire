3. TokenLedger (NEW, src/gameplay/match/token_ledger.gd, class TokenLedger extends RefCounted; TD-008: the stock and the loss live here, not in the controller)
  start(stock, types, player_count) copies stock.count_of(types[i].type_id) into counts[player][i]; count(player, type_index) -> int (0 outside the range);
  take(player, type_index) subtracts one, never below 0 (a take at 0 pushes one warning and changes nothing); carry_total(player) -> int is the sum of the counts
  of the types whose can_carry is true; has_lost(player) -> bool is carry_total(player) == 0; carrier_type_index() -> int is the index of the first type with
  can_carry or -1; first_problem(stock, types) -> String is the validation of section 2 ("" when fine). Class doc keeps the state table (copy at begin/restart,
  take at destruction, loss when the carry total is 0). Not a node, emits nothing, reads no input.

4. MatchController (AC-2, AC-4, AC-5)
- Holds one TokenLedger. begin(): validate (section 2) before anything else changes, then ledger.start(); restart(): ledger.start() again (both stocks full).
- choose(player, type_index): ALSO refused (false, nothing changes) when the Player has 0 Tokens of that type.
- _on_unit_destroyed(player): after garage.note_destroyed accepted and the Flag dropped, BEFORE unit_destroyed.emit: ledger.take(player, <index in unit_types of the
  destroyed Unit's stats; found by type_id>). So every listener of unit_destroyed already reads the new count. A destruction of a type not in unit_types: one warning, no take.
  The Token is taken at the DESTRUCTION, never at the spawn (the Unit in play is not yet subtracted).
- The loss: in _physics_process, after _apply_deliveries and while still RUNNING, _apply_losses(): the Players with ledger.has_lost(p). One loser -> RoundState OVER,
  _winner = the other Player. Both -> OVER with _winner = NO_WINNER (-1) (is_round_over() is then the only thing that tells "over, nobody won"). None -> nothing.
  The existing end of the tick (pause the tree, emit round_over(_winner)) announces it. A delivery that already set OVER this tick wins (the loss check does not run).
  "The same tick" = the same controller tick; every destruction source in this project runs before the controller in a frame (preflight to confirm).
- New read-only queries, no new signal: tokens_left(player, type_index) -> int (0 for a player/type outside the Round); carrier_type_index() -> int (-1 if none);
  can_choose(player, type_index) -> bool (tokens_left > 0). Class doc: the RoundState table gains both loss rows; winner_index() doc covers the double loss; the Player's
  state docs keep pointing at GarageQueue.
- AC-5: nothing else ends a Round: a type reaching 0, a Self-destruct or a Fuel crash that is not the last Motorbike Token end nothing.

13. PREFLIGHT CORRECTIONS (BINDING; they override sections 0-12 wherever they differ). Source: the design critic (14 issues, 20 missing cases) and the engine

13.1 Settled facts (engine, measured; open point 12a is closed)
  - Every REAL destruction source runs before the MatchController inside the same physics frame, so it is seen by that frame's controller tick: a Self-destruct (PlayerMatchInput,
    priority -1, calls Unit.destroy() synchronously), a Shot kill (the Shot is a child of World, tree order before the controller, it ticks the frame after it is fired and kills in
    its own tick), a Gyrocopter's Fuel crash (Unit._physics_process). Tab+Enter on one step destroy both Units in the same frame (both destroyed signals arrive before the controller's
    tick). A mixed double loss (a Self-destruct plus a Shot kill in one frame) is decided in that frame too: round_over(-1). The Unit's destroyed signal reaches the controller's
    _on_unit_destroyed synchronously, inside the Unit's tick, and a listener of unit_destroyed runs in the same call stack.
  - Once the controller sets paused = true at the end of the loss tick, no pausable node later in the frame ticks (a late +5 node did not): a destruction that would come after the
    controller in the same frame never happens in that Round. Only a process_mode ALWAYS node (RoundRestartInput and the Round-over screens, which destroy nothing) runs on.
    Therefore: "the same tick" = "before the controller's tick in the same physics frame"; a destruction one frame later than the first loss is not a double loss (the tree is paused).
  - The Unit's destruction by Self-destruct happens inside PlayerMatchInput's tick (priority -1), which is BEFORE PlayerChoiceInput's tick (priority -1, later in order) of the same
    frame: the choice input can act in the same frame as the destruction; a Shot kill comes after it, so the choice input acts a frame later. The cursor rule below handles both.
  - Pressing R in the same frame as the loss restarts at once (RoundRestartInput runs after the controller in the frame): the Round-over screen is then never drawn; harmless.
  - The loser's RespawnCountdown and UnitChoice are hidden by round_over; both views show the Round-over screen (P1 and P2: the same panel). The restart clears a standing choice
    (chosen_type_index -1, is_choosing true) and benches both Units (leave_play() emits no destroyed, no Token is spent by a bench or a restart).
  - GDScript: a negative index reads from the END of an array ([-1] is the last element, measured), so NO code may index unit_types() or a count array with carrier_type_index() or any
    index that can be -1 without checking it first. An untyped Dictionary variable assigned to a Dictionary[StringName, int] property is a RUNTIME SCRIPT ERROR; assign per key
    (stock.counts[id] = n) or use a typed literal. A reference to stock.counts writes THROUGH to the shared resource: the ledger and the runner must copy per key.
13.2 TokenLedger is KEYED BY type_id (replaces section 3's index keying)
  - Per Player a Dictionary[StringName, int] of counts keyed by UnitStats.type_id, filled by start(stock, types, player_count) with stock.count_of(types[i].type_id) per key (a copy by
    value; it never holds stock.counts). API: start(); count_of(player, type_id) -> int (0 for an unknown id or a Player outside the range); take(player, type_id) -> bool (subtracts
    one and returns true; at 0 or for an unknown id or Player it changes nothing, pushes ONE warning and returns false); has_lost(player) -> bool (the carrier's count is 0; false
    for a Player outside the range and before start()); carrier_type_id() -> StringName (&"" before start()); first_problem(stock, types) -> String.
  - Why: destruction.gd swaps controller.rules for a duplicate at runtime; by id the charge and the choice stay correct whatever the order or length of the live unit_types.
  - first_problem() returns ONE sentence naming the problem, or "". In this order: stock null ("the Map has no Token stock"); a negative count (names the type id); a stock key that
    matches no type_id of the types (names the key; a typo would silently make a type unavailable); an empty type_id or two types with the same type_id (names the indexes); the
    number of types with can_carry is not exactly ONE (none: "no Unit type can carry the Flag, so no Player could lose"; several: names their display names); the carrier's count is
    below 1 ("the Token stock gives no Token to <display_name>, the type that can carry the Flag, so a Player could neither carry a Flag nor lose"). begin() pushes that sentence as
    ONE push_error ("MatchController '%s': %s, so the Round does not begin.") after the existing checks and before anything changes (no bench, no connection, no signal, no state).
13.3 Controller API (replaces the signatures of section 4)
  - tokens_left(player_index: int, type_index: int) -> int: the ledger's count for unit_types()[type_index].type_id; 0 for a Player outside [0, players), a type_index outside
    [0, unit_types().size()), before begin() and after a refused begin(). can_choose(player_index, type_index) -> bool: tokens_left(...) > 0 and nothing else (it does not check the
    Round or the Player's state; choose() does). carrier_type_index() -> int: the index in unit_types() of the one carrier type, or -1 before a successful begin() and after a refused
    one. Document all three: read-only, no signal, safe to call from a handler of unit_destroyed (the Token is already taken).
  - choose(): refuses (false, nothing changes, no signal) a type with 0 Tokens; this is the SINGLE guard of AC-3. Section 5 (a refusal in GarageQueue._try_respawn) is DROPPED: it
    is unreachable (a Player with no Unit in play cannot lose a Token and choose() refuses an empty type), it could only clear the choice without a signal (the panel would keep
    showing "X ready") and no scenario could exercise it. garage_queue.gd is NOT edited. The deviation from the story's implementation note ("_spawn refuses") is logged.
  - _on_unit_destroyed(player_index): after garage.note_destroyed accepted and the Flag dropped, BEFORE unit_destroyed.emit: ledger.take(player_index, <the destroyed Unit's
    stats.type_id>). A Unit whose stats are null or whose type_id is not in the Round's types: ONE warning from the ledger, no Token taken, never a loss. A destruction while the
    Round is OVER (impossible today: nothing but ALWAYS nodes runs) still counts the Token; harmless because restart() refills.
  - winner_index() doc: NO_WINNER (-1) means BOTH "the Round runs" and "the Round ended and nobody won" (the double loss); only is_round_over() tells them apart, so a listener tests
    is_round_over() first. Do not add a second sentinel.
  - _apply_losses(): runs after _apply_deliveries while the Round is still RUNNING; a delivery that already set OVER wins (a dead branch in practice: a Carrier alive for the delivery
    cannot have spent its last Token; keep the guard, spend no scenario on it).
13.4 The cursor rule (replaces section 6)
  - PlayerChoiceInput._physics_process, in this order: (1) the existing guard (valid controller, is_choosing); (2) SNAP: if the cursor rests on a type with 0 Tokens, move it to the
    next type (increasing index, wrapping) that has Tokens, searching at most unit_types().size() steps; if no type has Tokens (one tick is enough for that to happen: the last
    Motorbike spent while every other type is at 0 - the loss is decided later in the same controller tick) the cursor stays and nothing happens (no hang, no error); emit
    cursor_moved ONCE and only when the index changed; (3) only then read the keys. A press on the first choosing tick therefore confirms the type the panel shows (it is never
    swallowed). (4) A steer key moves to the previous/next type that has Tokens (bounded search, wrapping) and emits cursor_moved once per move; with no other type available it
    moves nothing and emits nothing. With every type available the behaviour, including the two emits of a left and a right press on one tick, is IDENTICAL to today (the retained
    choice scenario counts emits: cursor_moves=10; the legacy 99 stock keeps it byte-identical). (5) Fire calls match_controller.choose(player_index, cursor) exactly as before.
  - UnitChoice._mark_slot() NEVER marks a slot whose count is 0, whatever the cursor says (between the destruction and PlayerChoiceInput's next tick, and in the all-zero tick, the
    cursor may rest on an empty type): such a slot wears slot_style/dim, never cursor_style.

13.10 Engine preflight, final additions (measured on 4.7.2, headless fixed-fps, windowed real-time and Map 01; logs in pf-engine/out/; the probe scripts pf_q2.gd, pf_q4.gd, pf_q7.gd, pf_kit.gd under
    pf-engine/probe/tools/evidence/split_screen/ are THROWAWAY REFERENCES for how to time a Self-destruct plus a lethal Shot on one frame; do not copy them into the repo)
  - The measured per-frame order (it replaces the order stated in section 0; Weapons come LAST, not before the Shots): PlayerDriveInput x2, PlayerMatchInput x2, PlayerChoiceInput x2
    (priority -1, tree order) > Map nodes, FuelCans, Units, PlayerFireInput x2, Shots, MatchController, RoundRestartInput (priority 0, tree order; RoundRestartInput is process_mode
    ALWAYS) > Weapon x2 (priority +1). A Shot fired in frame N first ticks in frame N+1. The loss check's guarantee rests on DEFAULT priority 0 plus tree position (World before the
    MatchController), not on a declared priority: the MatchController class doc states this as the contract it relies on, and the loss scenario asserts it (Tab+Enter and the
    mixed Self-destruct plus Shot double loss), so a changed tree order fails loudly.
  - A key event the harness injects at the start of a physics step, or in the idle phase after it, is first seen by the input nodes in the NEXT step (edge reads). A scenario waits at
    least TWO ticks after a press (the helper's press_settled plus one tick) before it reads a loss, a destruction or a restart, and never compares the press frame with the
    destruction frame for equality.
  - TokenStock fixtures: TokenStock.new() and counts[&"id"] = n per key (or a typed dictionary literal); NEVER an untyped Dictionary variable assigned to counts (runtime script error)
    and NEVER Resource.duplicate() of the shipped stock (it SHARES the counts dictionary with the cached .tres: measured, writing the copy changed the shipped stock); duplicate_deep()
    gives an independent copy. S1 corrects the line in token_stock.gd's class doc that recommends duplicate().
  - _on_unit_destroyed while the Round is OVER (possible only from a process_mode ALWAYS node or a harness coroutine; the game has none): the Token IS taken and unit_destroyed IS emitted
    but winner_index() cannot change (measured: tokens [0,0] with winner 1); benign because restart() refills; the controller's class doc says so, and a scenario that destroys during
    the pause expects exactly that.
  - Pressing R in the loss tick itself restarts the Round inside that tick (RoundRestartInput runs right after the controller): the Round-over screen is never drawn. Accepted and
    documented (a delay on R is outside the story); the same already holds for a delivery.
  - The winner may be a Player whose own Unit is destroyed at that moment (it lost a non-last Token earlier in the Round, or on the loss tick): the screen says "Player 2 wins!" while that
    Player's HUD band reads HP 0 / 40. A consequence of deciding by Tokens, not a bug; the evidence doc says so.
  - The frozen Shots are freed by SplitScreen._free_shots, a round_started listener; keep it a round_started listener (nothing in this story moves it). restart() keeps the order: seat
    flags, bench x2, state RUNNING, ledger.start(), tree unpaused, round_started.emit(), so every round_started listener reads full counts.
